Cell-DAG Extraction, explained from zero

How the matcher takes two graphs and picks the single cheapest correspondence between them — built up one idea at a time, assuming you know nothing.

0The problem it solves

Two drawings of the same thing. Which piece matches which?

Imagine two maps of the same neighbourhood, drawn by two different people. Both show the same streets, but one splits a road into more pieces, one rounds a corner differently, one labels things its own way. You want a machine to say: this piece here is the same road as that piece there. That correspondence — piece-by-piece, and the cheapest one that makes sense — is what the whole library computes.

Call the two drawings graph A and graph B. Each is a set of points joined by directed arrows (a road flows one way through it). The matcher has already done a lot of work before the step we're explaining. Extraction is the very last step: everything is prepared, and now we must read off the single best matching. This page is only about that final read-off — but it explains every word from scratch.

The one-sentence goal Out of millions of possible ways to line up A against B, extraction finds the one alignment with the lowest total cost — and does it without ever listing those millions.

1Vertices, candidates, and cells

The atoms of the whole algorithm.

A vertex is just a point in a graph. Points in A are A-vertices (written X, Y…); points in B are B-vertices (written u, v, w…).

An earlier step already looked at each A-vertex and found the handful of B-vertices near enough to be plausible partners. Those are its candidates.

Cell

A cell is a pair (X, v) — one A-vertex X paired with one of its candidate B-vertices v. Read it as a single guess: “maybe X matches v.”

Every cell carries a number, its emission E(X, v) — how badly X fits v (mostly how far apart they are). Small E = good fit.

The final answer, called M, is simply a chosen set of cells — for each A-vertex, which B-vertex (or vertices) it lands on. The cost of an answer is the sum of its cells' emissions, weighted by the rules in the next section. Extraction picks the set with the smallest total.

2The three moves

How you walk both graphs in step — and the only three things that can happen.

Think of tracing a finger along A and another along B at the same time, always moving forward. At each tick exactly one of three things happens. Each has a cost weight.

Advance

Both step forward

A moves to its next vertex and B moves to a next vertex. One-to-one. Normal progress.

weight 1

Stall

A steps, B waits

Several A-vertices pile onto the same B-vertex. Used where A is more detailed than B. Many-to-one.

weight β

Cover

B steps, A waits

One A-vertex spans several B-vertices in a row. Used where B is more detailed than A. One-to-many.

weight α

These three moves are the edges of a graph-of-cells — the “cell DAG.” Its dots are cells (X, v); a move is a legal step from one cell to another. So the whole task restated: find the cheapest connected trail of cells that covers every A-vertex.

One distinction to hold onto Advance and stall connect cells of different A-vertices (a parent and its child). Cover connects cells of the same A-vertex. That split is why, two steps from now, each cell will need two tables instead of one.

A word on “DAG”, “parent”, “child”

DAG = directed acyclic graph: arrows have a direction and there are no loops. In A, an arrow P → X makes P the parent and X the child — parent points to child, following the flow. A vertex with no incoming arrow is a source; one with no outgoing arrow is a sink.

3Runs — one A-vertex, several B-vertices

Because of cover, matches aren't always one-to-one.

When an A-vertex uses cover, it maps to a whole run of B-vertices in a row. A run has two ends, and they face opposite ways:

The tuple that records this run is (v, w, u) — its length is how many B-vertices the A-vertex covers. A plain one-to-one match is just a length-1 run like (u,). Keep the two ends — start and finish — in mind; the whole table design hangs on them.

4The dream that breaks

The obvious algorithm — and the small example that proves it wrong.

Here's the natural first idea. Give every cell one number (its best cost so far), walk the cell DAG in order, at each cell take the cheapest arriving option, add its own cost, pass it on. A clean scalar dynamic program. It would be fast and simple.

It's also wrong — and seeing exactly how is the key that unlocks everything after. Here is the smallest graph that breaks it.

Notice which B-vertex each cheap match forces the parent onto. There is exactly one arrow into each, so:

sink cellreached only fromso it demands J sits onits fit E
c₁ = uv₁ → uv₁0
c₁ = u′v₂ → u′v₂5
c₂ = dv₂ → dv₂0
c₂ = d′v₁ → d′v₁5

The scalar DP lets each child pick its own cheapest independently: c₁ grabs c₁ = u (cost 0, wants J = v₁), c₂ grabs c₂ = d (cost 0, wants J = v₂). It reports a total near 1. But J is one vertex — it cannot sit on v₁ and v₂ at once. That answer is a phantom: no real matching achieves it.

The real options — both children must leave J from the same cell:

pick (c₁, c₂)c₁ wants J onc₂ wants J onagree?real cost
(u, d)v₁v₂no — impossible—
(u, d′)v₁v₁yes1+0+5 = 6
(u′, d)v₂v₂yes1+5+0 = 6
(u′, d′)v₂v₁no — impossible—
The trap The true best is 6, not 1. The cheapest-looking pick, (u, d), is exactly the impossible one. The scalar DP fails because each child threw away the alternative the other child needed — and by the time they'd have to agree, the needed option was already gone.

Everything the real algorithm adds exists to avoid this one mistake: don't let a cell collapse to a single value while a shared decision is still open.

5Two tables per cell — and what's in a row

The data structure, defined exactly.

From Section 3, a run has two ends. Each is a separate concern, so every cell keeps two tables:

END[(X, u)] — the finish end

“X's run finishes at u.” This is the side the children attach to. Its recorded run so far is just (u,).

ENTRY[(X, v)] — the start end

“X's run starts at v.” This is the side the parent connects to. The whole run from v onward is already settled inside; v's own fit E is left unpaid — the parent will pay it, because the price depends on how the parent connects (weight 1 if it advances in, β if it stalls in), and the parent hasn't been reached yet.

So for one A-vertex with candidate cells {a, b, c} you get six tables: an END and an ENTRY for each. A single run v→w→u is filed twice — as a row in ENTRY[(X, v)] (its start) and in END[(X, u)] (its finish). The interior w is never an index; it just sits inside the tuple.

What a table is

A table is a small set of rows, all with the same three columns. Each row is one candidate partial answer:

valuependingcells — the matching so far
3.5{ }{ X:(u,), Y:(u,w) }
6.0{(m,w₁):F}{ X:(u,), … }
2.0{(m,w₂):F}{ X:(u,), … }
  • value — the total cost gathered so far (leaving out the unpaid entry and any unpaid pending items).
  • pending — unresolved shared decisions this row is carrying. Empty { } almost everywhere; explained fully in Section 9.
  • cells — the actual matching being built: for each A-vertex, its run of B-vertices. The answer travels inside the row; there's no separate backtrace.

The table only ever keeps the cheapest row per distinct pending. Two rows carrying the same pending are interchangeable → drop the pricier. Rows with different pending are genuine alternatives → both survive.

The whole trick in one line Where nothing is unresolved, pending is { }, so a table is exactly one row — your simple scalar DP. Tables grow past one row only at a merge, which is precisely where the scalar DP was wrong. The multi-row machinery is the fix, applied nowhere else.

6The sweep — vertices of A, sinks first

What we start with, and which way we go.

Before extraction begins we already have: every surviving cell, its emission E, and pruning flags (dead cells are gone). The END/ENTRY tables are empty — the sweep builds them.

The order runs over the vertices of A, not over individual cells: sort A's vertices topologically and walk them in reverse — sinks first, sources last. Each vertex gets one turn, and in that turn we compute all of its tables at once — an END and an ENTRY for every one of its candidates.

Why this direction: when we reach a vertex X, all of its children (downstream, nearer the sinks) are already done, so we can attach them; its parent (upstream) comes later, which is exactly why X defers its entry cost. The base case is a sink: with no children, its END is just the starting row (value 0, {}, {sink:(u,)}).

One more thing the sweep needs — the channel that carries a finished vertex's result to the next one: the inbox.

Inbox

Every vertex owns an inbox that its children fill. When a child finishes (earlier — sinks first), it drops its finished, already-priced rows into the inbox of the parent that will read them. So by the time a vertex's turn arrives, everything it needs is already sitting there.

A row is filed by which cell of the parent it attaches to and which child sent it. The slot inbox[X][u][c] means: “the rows from child c, waiting at X's cell u.”

That inbox is the input to building a vertex's tables — the next section shows exactly how. (Its full life — when it fills, when the vertex pushes onward, when it's freed — is Section 8.)

7Building the tables, candidate by candidate

One vertex's turn = two passes: every END, then every ENTRY. Each is a plain input → calculate → output.

On vertex X's turn we sweep its candidates twice — Pass 1 builds every END[(X,u)], Pass 2 builds every ENTRY[(X,v)]. The thing to get straight is that the two tables read different inputs:

building this tablereads as inputand combines them by
END[(X,u)]the inbox at u (each child's rows) + a base rowcross-join over children
ENTRY[(X,v)]END[(X,v)] + X's own ENTRY of the next candidatetake the cheaper (cover)

So only END reads the inbox; ENTRY is built entirely from tables X already holds. Running example: A is one arrow X → Y; B has u → w; emissions E(Y,u)=3, E(Y,w)=1; α=β=1. Child Y finished earlier and already pushed its two priced options into X's inbox at cell u.

Pass 1 — building END[(X,u)]  stage: read the inbox

Input. The bare row for X at u, plus — for each child — that child's option-list from the inbox slot at u. One child here, Y:

# what Y left in X's inbox at cell u  (Y already paid its own connect cost):
inbox[X][u][Y] = [ (3, {}, {Y:(u,)}),   Y stalled on u   → paid β·E(Y,u)=3
                 (1, {}, {Y:(w,)}) ]  Y advanced u→w  → paid 1·E(Y,w)=1

base row     = (0, {}, {X:(u,)})
Why is the base value 0, not E(X,u)? E(X,u) is X's own entry cost, and by the deferral rule (Section 3) an entry's emission is left unpaid inside the state. It's paid later — by whoever connects to X (its parent, at weight 1 or β), or as α·E(X,u) if the run later covers past u. So the base starts at 0 and only gathers the children's costs.

Calculate. Cross-join: combine the base with one option per child (values add, cells merge, pending merge), then keep the cheapest per pending. With a single child it's just “base + each of Y's options, keep the cheaper”:

base + (3, {Y:(u,)})  =  (3, {}, {X:(u,), Y:(u,)})
base + (1, {Y:(w,)})  =  (1, {}, {X:(u,), Y:(w,)})   ← cheaper

OUTPUT  END[(X,u)] = (1, {}, {X:(u,), Y:(w,)})

Output. One table, END[(X,u)] = (1, {}, {X:(u,), Y:(w,)}). With one child there was nothing to “cross-join” — we just kept Y's cheaper option. The cross-join only shows itself with two or more children, so let's do that next, because it's the part that matters.

What “combine” and “cross-join” actually mean

Combine two rows — written ⊕

To fuse row (v₁, p₁, c₁) with (v₂, p₂, c₂) into one:

1. Add the values: v₁ + v₂.   2. Union the cells: c₁ ∪ c₂ — they describe different A-vertices, so they never clash.   3. Union the pending: p₁ ∪ p₂ — empty here; at a merge, the same merge-vertex appearing with two different cells makes the fusion impossible, so that combination is dropped.

Now the same END build, but X has two children, Y and Z, both waiting at u. Cross-join = start from the base row and fuse in one option from every child, trying all combinations:

inbox[X][u][Y] = [ Y₀=(3,{},{Y:(u,)}),  Y₁=(1,{},{Y:(w,)}) ]
inbox[X][u][Z] = [ Z₀=(4,{},{Z:(u,)}),  Z₁=(1,{},{Z:(w,)}) ]
base           =   (0,{},{X:(u,)})

# fuse base ⊕ (one Y) ⊕ (one Z) — all 2×2 = 4 combinations:
base ⊕ Y₀ ⊕ Z₀  = (3+4 = 7, {}, {X:(u,), Y:(u,), Z:(u,)})
base ⊕ Y₀ ⊕ Z₁  = (3+1 = 4, {}, {X:(u,), Y:(u,), Z:(w,)})
base ⊕ Y₁ ⊕ Z₀  = (1+4 = 5, {}, {X:(u,), Y:(w,), Z:(u,)})
base ⊕ Y₁ ⊕ Z₁  = (1+1 = 2, {}, {X:(u,), Y:(w,), Z:(w,)})   ← cheapest

# all four carry pending {} → same signature → keep only the cheapest:
END[(X,u)] = (2, {}, {X:(u,), Y:(w,), Z:(w,)})

That is the merge, in full: every combination of one option per child, each fused with ⊕, then the cheapest kept per pending. Two children → 2×2 combinations; three → 2×2×2; and that multiplication is the seed of the slowdown we reach in Section 11 — harmless here only because every row's pending is {}, so they all collapse to one.

Pass 2 — building ENTRY[(X,v)]  stage: read END + cover

Input. No inbox this time. ENTRY[(X,v)] reads two tables X just computed: its own END[(X,v)], and its own ENTRY[(X,w)] for the candidate w one B-step later. That's why Pass 2 walks candidates finish-end first — the “next” one is always ready.

Calculate. This one is not a cross-join — there are no children to fuse. It's a plain min between two rows: “the run ends right here” (END[(X,v)]) versus “extend the next candidate's run by one cover step” (ENTRY[(X,w)] with +α·E and v prepended). Keep the cheaper, per pending:

# the COVER branch: extend the run, paying α·E for each cell it covers past.
# For E(X,u)=1, E(X,w)=2, building the run v→w→u:
run (u,)     :  0                          just the finish; entry u unpaid
run (w,u)    :  0 + α·E(X,u)=1  =  1        covered u; entry w unpaid
run (v,w,u)  :  1 + α·E(X,w)=2  =  3        covered w; entry v unpaid

So ENTRY[(X,v)] for the full run carries value 3 (its cover charges), with the entry v still unpaid. And note the min: since extending only adds α·E, ending early is cheaper on its own — the run extends only when it is forced to reach a later finish, for instance because X's children attach at u, so the run must span down to u to carry them.

Output. One ENTRY table per candidate. An interior candidate's table is never empty — it is the stepping-stone the longer runs are built from. When Pass 2 ends, every table of X exists; only then does anything leave the vertex — which is Section 8.

8The lifecycle — inbox, push, free

A table lives for exactly one turn: born, used, pushed onward, freed — then never touched again.

We met the inbox in Section 6 (each vertex's mailbox, filled by its children). Now watch a vertex's whole life around it, in three phases:

  1. Before X's turn — the inbox fills. Each child of X, on its own earlier turn, dropped its rows into X's inbox. Nothing of X itself exists yet; the inbox just accumulates across those turns.
  2. X's turn — everything happens here. read the inbox (all children's rows are present)  →  build every END[(X,u)] (Pass 1)  →  build every ENTRY[(X,v)] (Pass 2)  →  push the ENTRY rows into the parent's inbox  →  free X's tables and inbox.
  3. After X's turn — the table is gone. The END/ENTRY objects are dropped. Only the rows survive — sitting, by reference, in the parent's inbox, waiting for the parent's turn.

So, plainly: a table is born on its vertex's turn, is never updated afterward (it is built complete in that one turn), and dies at the end of the turn.

Per table, or per vertex? The push is per vertex, once — at the very end of the turn. X finishes all its END tables, then all its ENTRY tables, and only then, in a single batch, prices its finished ENTRY rows and drops them into its parent's inbox. Nothing leaves X table-by-table; a half-built vertex emits nothing.

Where the push goes — parent vertex, or parent cell?

Both, at two granularities. The inbox belongs to the parent vertex P. But each pushed row is addressed to a specific cell of P, and tagged by which child sent it. The mailbox slot is:

inbox[ P ][ u ][ X ]  =  the rows
        ↑      ↑      ↑
      parent  parent   child
      vertex  cell u   X

Which parent cell u? The one that X's entry e can legally connect to — either u = e (a stall) or e one B-step past u (an advance). So when P's turn comes and it builds END[(P,u)] in Pass 1, the child rows it folds in are exactly the ones waiting in inbox[P][u]. The push and the read line up perfectly — that is the whole handoff between a child and its parent.

One caveat, picked up next section

If X has several parents — meaning X is a merge — only one of them (the “absorber”) receives the pushed rows; the other arms are handled a different way. That is exactly what Section 9 is about.

Why it can die so fast Once X is done, nothing downstream needs it (already processed), and its parent reads it only through the rows already pushed. So the only thing ever held in memory is the set of unprocessed inboxes — the sweep's moving frontier — never all the tables at once.

9Pending — the merge, where alternatives are born

The one place tables grow past a single row — and the reason the whole design exists.

Merge

A merge is an A-vertex with more than one parent — two arrows point into it. Its parents are its arms. The arms must end up agreeing on which cell the merge sits in; enforcing that agreement is the entire job of pending.

The smallest merge that shows the point:

Turn 1 · vertex m (the sink). Sweep sinks-first, so m goes first; its two cells, entry unpaid:

m@w₁:  (0, {}, {m:(w₁,)})        m@w₂:  (0, {}, {m:(w₂,)})

Turn 2 · vertex p₁ (the absorber arm). It consumes m from its inbox — but it cannot pay m's entry yet, because the other arm hasn't been seen and both must land on the same cell of m. So instead of paying, it defers: pending is born, one row per candidate cell of m:

(0, {(m,w₁):F}, {p₁:(a,), m:(w₁,)})   ← assumes m enters at w₁
(0, {(m,w₂):F}, {p₁:(a,), m:(w₂,)})   ← assumes m enters at w₂

These two rows carry different pending, so — the crucial break from the scalar DP — p₁ is not allowed to keep only the cheaper. It keeps both.

Turn 3 · vertex p₂ (the other arm). It is not the absorber, so it contributes only markers — one per cell of m, carrying the same pending but no cells of its own yet. These are what the two arms will later be matched on.

What pending is pending = {(merge, its assumed cell): stall-flag}. In words: “keep one alternative per possible cell of the shared merge, so the other arm can still choose the one that agrees.” That's the whole of it — and it's exactly what was missing in Section 4.

Why one absorber, not two half-cost copies?

There's a tempting, fully symmetric alternative: send all of m's rows to both parents unchanged, but halve each row's cost. At the join the two halves add back to the full cost, and since both parents got the same rows they agree on m's cell. This is correct — no phantom, no double-count. So why the lopsided absorber instead?

Because a row has two parts that behave differently under “halve”:

  • the cost is a single number — halving it is fine, and the halves sum cleanly at the join;
  • the cells — m's entire downstream matching M — cannot be halved (there is no such thing as half a matching), so each parent must carry the full copy.

So under the half-cost scheme, m's whole cone-matching would sit duplicated on both arms, and stay duplicated for the entire stretch from m up to wherever the arms rejoin. That matching is the big part of a row (it grows with the cone); the cost is one float. You'd pay ~2× memory on m's cone just to split a single number.

The absorber sidesteps it by not splitting at all:

halve the cost, send to bothabsorber (what the code does)
m's cost½ on each arm, sums at the joinfull on the absorber, 0 on the other
m's cells (M)full copy on both arms (duplicated)full on the absorber, {} on the other
memory on m's cone~2×1×
correctnesscorrectcorrect

Both give the identical answer and keep the same number of rows — you still hold the alternatives on both sides either way. The asymmetry buys nothing in correctness; it exists solely so the expensive part, M, travels on one arm instead of two.

10Discharge, and reading off the answer

How the kept alternatives collapse back to one.

The deferred entry can't stay unpaid forever. It is discharged — paid once and dropped — at the moment the merge's arms finally meet. When both arms are in one row, we check they picked the same cell of m (mismatches are thrown away), pay E(m,·) a single time, and remove the pending key. Continuing the example to the end, where the two source arms combine:

sources pay their own entries first: p₁ +0 ; b₁ +5, b₂ +0
{m@w₁} × {m@w₂}   → same merge, different cell → conflict, discarded
{m@w₁} × {m@w₁}   → agree → (5, {(m,w₁):F}, all cells)
{m@w₂} × {m@w₂}   → agree → (0, {(m,w₂):F}, all cells)

discharge (pay E(m,·) once, drop the key):
   5 + E(m,w₁) = 6            0 + E(m,w₂) = 2
no keys left → rows comparable → take the min:  2  ✓ the true optimum

Because both alternatives were kept, the arm with the cheap-but-picky option (b₂, which only pairs with w₂) could still find its partner, and the correct answer 2 survives — where the scalar DP had thrown it away. Once the last vertex is folded, the surviving row with the lowest value that passes the validity rules is the answer M — already sitting in its cells field.

11When it gets slow

Where the elegance has a price — and the exact shape of the trouble.

Count the rows. A stretch with no merge carries pending = {} everywhere, so every table is one row — fast, scalar, ideal. One merge with k candidate cells means up to k live rows — still cheap.

The danger is two or more merges open at the same time. Their pending markers coexist, and the number of distinct combinations becomes the product of their cell counts — k₁ × k₂ × …. Rows multiply instead of add.

The escape valve — and its blind spot There's a rescue called early discharge: pay off a merge's pending as soon as its arms rejoin at a shared ancestor, so it never lingers to multiply with the next merge. It works beautifully when the graph's branches reconverge. But if A is a tree — branches that split and never rejoin — a merge's arms share no ancestor, early discharge never fires, and every merge's pending survives to the very end. Several merges in a tree, and the product blows up.

That is the crux worth remembering: the algorithm is a clean scalar DP everywhere except at merges, and merges are handled cheaply as long as their alternatives get discharged early. The pathological case is a tree-shaped A with more than one merge — exactly the situation where early discharge has nothing to grab onto, so the kept alternatives pile up multiplicatively. Knowing that tells you precisely where to look when the extraction is slow, and precisely what a fix has to change: give the tree case a way to discharge that doesn't depend on branches ever meeting again.
